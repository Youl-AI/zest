# Implementation decisions

Decisions made at the implementer's discretion while building Lime for Windows; later tasks append here.

- Task 1: xunit.v3 runs on Microsoft.Testing.Platform via `global.json`, so the test command is `dotnet test --project tests/LimeWin.Core.Tests` (the positional form fails on SDK 10).
- Task 1: Gif targets are the writable video formats; Video targets add gif+mp3.
- Task 1: pdf->txt is not Office-gated (PdfPig handles it).
- Task 1: `OutputNaming.UniquePath` treats an existing directory with that name as taken.
- Task 2: `FormatOf` returns null for an existing directory (so a folder named `x.png` is not treated as an image); a folder among the dragged paths empties Convert and Tools, Actions stay at 5.
- Task 2: Crop appears only when exactly one image is dragged (multi-image drops omit it).
- Task 2: Convert offers the intersection of every file's targets in the first file's order; any unknown format or folder yields an empty list. Tools: raster images only (jpg png webp heic tiff avif bmp; svg excluded), or PDFs only; mixed yields empty.
- Task 3: Drag threshold is per-axis (`|dx| > px || |dy| > px`, strictly greater), following the Windows SM_CXDRAG convention, not Euclidean distance.
- Task 3: `WheelGeometry.PetalAt` treats the Inner and Outer radii as inclusive; gutters are constant-width strips (angular half-gutter = asin(Gap/2/r)); `BearingOf` returns the petal's centre in radians.
- Task 4: SVG rasterization stays at 192 DPI (density 192, 2x), so `FixtureFactory.Image` writes SVG sources at half size (w/2 x h/2 user units) and every source in the Routes theory decodes to 64x48.
- Task 4: CapabilityProbe on this machine with Magick.NET 15.0.0 (Q8-AnyCPU): HEIC write = false, AVIF write = true. The Routes theory skips heic as target and as source (the fixture cannot be written); avif is fully covered.
- Task 4: ConversionRouter checks the source folder is writable by creating/deleting a temp file before calling the converter, and after any converter exception deletes exactly the paths the converter registered with `ctx.Track` (tracked folders recursively), then rethrows (see the Task 4 fix bullet).
- Task 4: ImageConverter decodes from bytes (content decides the decoder, so a PNG named .jpg works); Magick decode exceptions map to `LimeException("이미지를 읽을 수 없습니다.")` and encode/save exceptions to `"이미지를 저장하지 못했습니다."`. Alpha is flattened to white for jpg and bmp only. PNG uses define png:compression-level=6.
- Task 4: PDFsharp 6.5.0 turned out to be AGPL-3.0-only (license key required at runtime; 6.2.4 is the last MIT release). Pin lowered to 6.2.4 and referenced only by the test project; image->PDF is written with PdfPig's `PdfDocumentBuilder` (page = pixel size in pt, `AddPng` fills the page). PDF tests verify with PdfPig.
- Task 4: Enabled `CentralPackageTransitivePinningEnabled` and pinned transitive System.Security.Cryptography.Pkcs to 10.0.13 (8.0.1 and 10.0.0 carry NU1902/NU1903 advisories); build is warning-free.
- Task 4 fix: failure cleanup no longer diffs the folder. Converters call `ctx.Track(path)` for each output file/folder BEFORE creating it (`OperationContext.Created`, thread-safe); on any exception the router deletes only tracked paths (folders recursively), so files other processes create meanwhile are never touched. ImageConverter maps decode failures to "이미지를 읽을 수 없습니다.", encode failures to "이미지를 저장하지 못했습니다.", and source IO/permission errors to "원본 파일을 열 수 없습니다.".
- Task 5: PDF pages are rendered by PDFtoImage 5.4.0 (PDFium, SkiaSharp) at 200 DPI with the longest edge capped at 4096 px (explicit Width/Height computed from the page size in points), white background. Encoding uses SkiaSharp directly (jpg quality 80, png) instead of Magick; SkiaSharp comes in transitively. The original app uses 150 or 200 DPI depending on the path; this port uses 200 everywhere.
- Task 5: Every PDFtoImage/PDFium call goes through one static `SemaphoreSlim(1,1)` in `PdfRenderer` (PDFium is not thread-safe) and runs on a pool thread. The gate is taken per page, so cancellation is observed between pages. The PDF is read into a byte array once per call, so the source file is not locked while rendering.
- Task 5: PDF error mapping: password-protected (PDFium `PdfPasswordProtectedException` or PdfPig `PdfDocumentEncryptedException`) -> "암호로 보호된 PDF는 열 수 없습니다." with no prompt; empty, corrupt or otherwise unreadable -> "PDF를 읽을 수 없습니다."; PDF without any text -> "이 PDF에는 글자 정보가 없습니다. 도구 휠의 '글자 복사'를 쓰세요.".
- Task 5: pdf->txt uses PdfPig `ContentOrderTextExtractor` per page, pages joined by one blank line, UTF-8 without BOM. One-page PDFs produce a single `ConvertOutput` file, multi-page PDFs a `CreatePagesFolder` folder (tracked right after creation) with `PageFileName` files.
- Task 5: PDFsharp 6.2.4 core has no Windows font access (`UseWindowsFontsUnderWindows = true` still fails with "No appropriate font found"), so `FixtureFactory.Pdf` registers a small test-only `IFontResolver` that loads C:\Windows\Fonts\malgun.ttf (Malgun Gothic) for the Hangul text.
- Task 6A: `CapabilityDetector` (Core) treats Office as available only when `Word.Application`, `PowerPoint.Application` and `Excel.Application` each have a non-empty `HKCR\<ProgID>\CLSID`; Ffmpeg = `ffmpeg.exe` in a `PATH` folder (entries trimmed and unquoted, blank/malformed entries skipped; no PATHEXT or App Paths lookup). `FindOnPath` is public so it can be tested without touching the real PATH.
- Task 6A: `Services` is a static class (`Services.Start()` once in `App.OnStartup`; `Capabilities`, `Router`, `Jobs` throw if read before that). The router gets `ImageConverter` and `PdfConverter`, the converters that exist now.
- Task 6A: Win32 placement helpers live in one internal `Native.cs` (virtual screen, monitor at a point, GetAsyncKeyState, SetWindowPos, extended styles); the hook P/Invoke stays in `LowLevelHooks`.
- Task 6A: The hooks track left/right Shift/Ctrl/Alt separately and post a sample only when the modifier set, the left button, or (while the button is held, latest-point coalesced, at most one in flight) the cursor changes. Esc is the only other key looked at; nothing is stored. Injected events are skipped entirely.
- Task 6A: The drop overlay keeps the spike's exact window setup (no extra extended styles) and swallows `WM_DPICHANGED` so a surface spanning mixed-DPI monitors keeps its physical virtual-screen bounds. Petal hit-testing uses `GetCursorPos` (physical pixels) against the wheel centre and scale (physical px per canvas unit = wheel window width / 320).
- Task 6A: The wheel window is a fixed 320x320 DIP window with `WS_EX_TRANSPARENT|WS_EX_LAYERED|WS_EX_NOACTIVATE|WS_EX_TOOLWINDOW` so drops fall through to the overlay. It is moved twice (move, let WPF rescale for the target monitor's DPI, move again with the final size) and is clamped inside the cursor's monitor so every petal stays reachable near screen edges; the overlay hit-tests against the clamped centre.
- Task 6A: The wheel window and overlay are created once and hidden/shown per drag, not recreated.
- Task 6A: The drop returns `DragDropEffects.Copy` on a petal and `None` elsewhere; never `Move`, which would let Explorer delete the source.
- Task 6A: Tool and action petals start a JobRunner job that throws `LimeException("준비 중입니다.")`, so they show as a failed card titled with the petal label (closed by click) until their tasks land.
- Task 6A: Done and cancelled cards close themselves after 4 s; failed cards close on click. A done card with results opens `explorer.exe /select,"<first result>"` on click. The cancel button cancels the job's token and shows "취소하는 중…" until the job ends.
- Task 6A: Progress cards stack in one borderless topmost no-activate window (SizeToContent) in the bottom-right of the work area, 12 DIP margin. The monitor is the one under the cursor when the first card of a batch appears and stays fixed while any card is visible.
- Task 6A: "휠 켜기" is on at every start (not persisted). Turning it off uninstalls both hooks and closes any open wheel. The single-instance mutex is `Local\LimeWin.SingleInstance`; a second instance exits silently with code 0.
- Task 6A: H.NotifyIcon `ForceCreate(enablesEfficiencyMode: false)`: Efficiency Mode would lower the process priority and slow the hooks and conversions. The placeholder tray icon is a `GeneratedIconSource` "L" on lime green until Task 6B draws the real one.
- Task 6A: The app follows the system light/dark theme via `ApplicationThemeManager.ApplySystemTheme()` at startup and again on `SystemEvents.UserPreferenceChanged` (General/Color), since there is no main window for `SystemThemeWatcher` to watch. `NOTICE.md` is embedded into the exe as a resource for the license window.
- Task 6A: WPF-UI 4.3.0's implicit Window style sets `MinWidth=460`/`MinHeight=320`, which made the wheel window 460x320 (breaking its centring and hit-test scale) and padded the card stack. The overlay, wheel and card-host windows set `MinWidth`/`MinHeight` to 0 locally.
- Task 6A fix: the close rules moved to the pure, tested `LimeWin.Core.Wheel.OverlayCloseRules` (events + a monotonic clock in, Keep/AwaitDrop/Close out). The 500 ms fallback is measured from the first release and never restarted; `WheelController` arms a one-shot 500 ms timer once per drag, and the 100 ms safety tick covers a timer that fires early.
- Task 6A fix (controller ruling, overrides brief line 25): a DragEnter without FileDrop (text, zip contents, MTP items) closes the overlay at once so OLE re-targets the window underneath; such drags are no longer swallowed.
- Task 6A fix: the hooks run on a dedicated background STA thread ("LimeWin input hooks") with a bare GetMessage pump; `Uninstall` posts WM_QUIT and joins it (2 s cap). Every 5 s the app compares `GetLastInputInfo` with the time of the last hook callback (any callback, injected included); input more than 2 s newer means Windows dropped the hooks, so they are reinstalled. Input on the secure desktop can trigger a harmless reinstall.
- Task 6A fix: on every left-button-down the hook re-reads the six modifier keys with GetAsyncKeyState, so a key-up lost to the secure desktop or UIPI cannot leave a modifier stuck.
- Task 6A fix: hook install failure turns "휠 켜기" off and shows the tray balloon "키 감지를 켜지 못했습니다." Unhandled dispatcher and unobserved task exceptions are marked handled: the overlay is closed and the balloon "예기치 않은 오류가 발생했지만 Lime은 계속 실행됩니다." is shown. Nothing is logged.
- Task 6A fix: dropped items start their jobs through `Dispatcher.BeginInvoke`, after OLE's Drop callback has returned. The card host is placed while hidden (size estimated at the target monitor's DPI from `GetDpiForMonitor`), then shown and re-placed exactly.
- Task 6A fix 2: startup runs inside try/catch; on failure a MessageBox "Lime을 시작하지 못했습니다: <message>" is shown and the app shuts down. The last-resort exception handlers are subscribed only after startup succeeds, and `OnExit` releases the single-instance mutex in a `finally`. The error balloon is shown at most once per 30 s.
- Task 6A fix 2: `LowLevelHooks.Uninstall` forgets the hook thread only after it has joined (2 s); until then `Installed` is false and `Install` waits up to 2 s more, then refuses with `InvalidOperationException`, which "휠 켜기" reports like an install failure (unchecked + balloon).
- Task 6B: All wheel values live in `Wheel/WheelStyle.cs` (light and dark `WheelPalette`, geometry, type, motion). Geometry follows the original: disc radius 136 (outer + 8) with a 1 px lime ring at 35 % (`#598BC34A`, the original's `Brand.accent.opacity(0.35)` stroke) plus the brief's 0.5 px `#40FFFFFF` inner line, hub radius 44 (hole * 2 - 4 wide), label radius 93, corner fillets outer 9 / inner 5 clamped to 30 % of an edge as in the original. Petal corners are exact fillets (tangent to the side line and the ring) rather than the original's arcTo approximation.
- Task 6B: The highlighted petal uses the original's vertical gradient, lime at 82 % (`#D18BC34A`) at the canvas top to solid lime at the bottom, with a 1 px `#80FFFFFF` hairline (original: white 0.5 stroke). Dark uses the same with `#6FA83A`.
- Task 6B: The hub circle is always drawn (empty until a petal is highlighted) because every reference shows it; light hub `#B3FFFFFF` (original glass value). Hub text 13 px: Segoe UI Variable Display Semibold for formats, Pretendard SemiBold for Korean labels.
- Task 6B (deviation): dark film `#D91C1C1C` (brief `#B31C1C1C`) and dark petal `#CC484848` (brief `#CC3A3A3A`). Over a bright page the brief values put the petals below the disc (about #41 vs #5D), the opposite of the brief's "petals one step lighter"; the new pair keeps petals about one step above the disc on white and on black and matches the original dark wheel (disc ~#1E, petals ~#40). Dark hub `#14FFFFFF` (a step above the disc, like the reference's #2E hub) instead of the original glass value black 30 %, which read as a dark hole.
- Task 6B (addition): each petal has a 1 px hairline (`#14000000` light, `#14FFFFFF` dark). With the brief's light values over a blank white page the disc and petals differ by only about 7 levels and the gutters vanished; the hairline keeps the petal shapes readable.
- Task 6B: Tool/action icons are Segoe Fluent Icons 20 px: compress E73F (BackToWindow), crop E7A8 (Crop), images to PDF EA90 (PDF), merge EA3C (Merge), split E8C6 (Cut), copy text E8D2 (Font), remove background E75C (EraseTool), shelf E7B8 (box/tray), copy E8C8 (Copy), move E8DE (MoveToFolder), copy path E71B (Link), terminal E756 (CommandPrompt). Progress card states use E7C3 (page, running), E930 (Completed, done), E783 (Error, failed), E711 (Cancel, cancelled).
- Task 6B: Petal labels never wrap mid-word: a label wider than 80 % of the petal chord at the label radius is broken at spaces only ("PDF / 만들기" on 9 petals). WPF would otherwise split Hangul words between syllables.
- Task 6B: The wheel and card use `TextFormattingMode=Display` / `TextRenderingMode=Grayscale` on screen. The `--render` harness switches its instances to Ideal because RenderTargetBitmap rasterizes Display text at 96 DPI and stretches it to 2x; Ideal is what a 200 % screen effectively shows.
- Task 6B: Glass: `BackdropCapture` BitBlts the wheel window's physical rect (SRCCOPY, no CAPTUREBLT) once when the wheel is first drawn, after the window is placed and before it is shown; the capture is forced to Bgr32 so an undefined alpha byte can never make the glass see-through. A mode switch keeps the first capture. The blurred layer has a `BitmapCache` so the radius-24 blur is not recomputed on every frame of the highlight animation. If the capture fails, the disc uses the opaque tint (`#FF` alpha).
- Task 6B: Motion uses `SplineDoubleKeyFrame`/`SplineColorKeyFrame` with KeySpline(0.23,1,0.32,1) and CSS ease (0.25,0.1,0.25,1), started without `From` and with SnapshotAndReplace, so an interrupted highlight continues from where it is. Highlight color is a 100 ms opacity crossfade of a lime overlay plus a 100 ms text color change. With Windows animation effects off the lift is dropped entirely (no instant jump) and color/opacity changes stay.
- Task 6B: Cancel fade: every overlay close that is not a drop on a petal (Esc, button-up outside, hole, safety tick) hides the overlay at once and fades only the wheel window (100 ms) before hiding it; a drop on a petal and programmatic `Close()` (wheel off, recovery, exit) hide at once. A new drag during a fade cancels the fade first.
- Task 6B (deviation): the progress card surface is not real Mica. The card host must stay a layered (AllowsTransparency) window for the 8 px enter/exit motion and the stacked shadows, and DWM backdrops do not apply to layered windows; the card uses WPF-UI's Mica fallback brush (`ApplicationBackgroundBrush`), `SurfaceStrokeColorFlyoutBrush` 1 px border, 8 px corners and a soft shadow (blur 16, depth 3, 16 %). Each card carries 12 DIP of transparent padding for the shadow, so the host's extra margin is now 0 (cards still sit 12 DIP from the work-area edge). Exit is 150 ms opacity plus 8 px back down (the way it came in); done cards hide the progress bar.
- Task 6B: Tray glyph: monochrome lime slice drawn with WPF geometry per size (16/20/24/32) into a PNG-entry .ico in memory, picked at the small-icon metric for the system DPI. Rind ring around six segments cut with the wheel's own petal geometry; at 16 and 20 px the segments are plain wedges meeting near the centre because rounded teardrops blurred into dots. `#1F1F1F` on a light taskbar, white on a dark one (`SystemUsesLightTheme`, dark when unset), swapped on `UserPreferenceChanged`.
- Task 6B: `--render <folder>` skips the single-instance mutex, tray and hooks. Beyond the brief's set it also writes 5-petal (actions), empty-state, 7-petal over plain white and plain black, dark progress cards and a tray-icon sheet, plus `render.log` with the font file each typeface resolved to. The 9-petal set is all five tools plus four actions, since no real wheel has nine items.
- Task 7: ffmpeg is the first `ffmpeg.exe` on PATH (`FfmpegLocator.Locate`, shared by `CapabilityDetector` and `Services`). On this machine that is the WinGet "Links" symlink, which runs fine as is. `ffprobe.exe` is looked up next to the found path, then next to its symlink target (`File.ResolveLinkTarget`), then on PATH; without ffprobe progress simply stays at 0 until the end.
- Task 7: targets whose encoder this ffmpeg lacks are dropped at startup, not hardcoded. `FfmpegLocator.UnavailableTargets` runs `ffmpeg -encoders` once and checks the `-c:a`/`-c:v` values of each table row; the result is `Capabilities.UnavailableTargets` (new optional field) and `FormatCatalog` hides those targets. The brief's libvorbis/ogg case is covered by this; gyan.dev full 8.1.2 has all nine encoders, so nothing is dropped here. If the encoder list cannot be read, nothing is dropped.
- Task 7: `FfmpegConverter.Handles` follows the catalog: audio to audio targets; video to video targets plus gif and mp3; GIF to video targets. webm is input only. The ffmpeg run adds `-progress pipe:1 -nostats` in front of the table arguments (`FfmpegArgs.For` stays the pure table).
- Task 7: failure message is `변환 실패: <last stderr line>` (last 20 stderr lines are kept, drained asynchronously). Cancel kills the process tree and waits for exit before throwing OperationCanceledException, so the router can delete the tracked output.
- Task 7: the full audio/video/GIF matrix (105 routes, 2 s clips, plus a 120 s cancel test) takes about 24 s, so it was not reduced.
- Task 7 (controller ruling): mp4, mov and mkv (libx264) get `-vf scale=trunc(iw/2)*2:trunc(ih/2)*2` before the codec arguments, because libx264 fails on odd width/height (common for GIF sources). GIF output uses filter_complex and is unaffected; non-x264 targets are unchanged.
