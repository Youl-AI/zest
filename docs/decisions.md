# Implementation decisions

Decisions made at the implementer's discretion while building Lime for Windows; later tasks append here.

- Task 1: xunit.v3 runs on Microsoft.Testing.Platform via `global.json`, so the test command is `dotnet test --project tests/LimeWin.Core.Tests` (the positional form fails on SDK 10).
- Task 1: Gif targets are the writable video formats; Video targets add gif+mp3.
- Task 1: pdf->txt is not Office-gated (PdfPig handles it).
- Task 1: `OutputNaming.UniquePath` treats an existing directory with that name as taken.
- Task 2: `FormatOf` returns null for an existing directory (so a folder named `x.png` is not treated as an image); a folder among the dragged paths empties Convert and Tools, Actions stay at 5.
- Task 2: Crop appears only when exactly one image is dragged (multi-image drops omit it).
- Task 2: Convert offers the intersection of every file's targets in the first file's order; any unknown format or folder yields an empty list. Tools: raster images only (jpg png webp heic tiff avif bmp; svg excluded), or PDFs only; mixed yields empty.
- Task 3: Drag threshold is per-axis (`|dx| > px || |dy| > px`, strictly greater), following the Windows SM_CXDRAG convention, not Euclidean distance.
- Task 3: `WheelGeometry.PetalAt` treats the Inner and Outer radii as inclusive; gutters are constant-width strips (angular half-gutter = asin(Gap/2/r)); `BearingOf` returns the petal's centre in radians.
- Task 4: SVG rasterization stays at 192 DPI (density 192, 2x), so `FixtureFactory.Image` writes SVG sources at half size (w/2 x h/2 user units) and every source in the Routes theory decodes to 64x48.
- Task 4: CapabilityProbe on this machine with Magick.NET 15.0.0 (Q8-AnyCPU): HEIC write = false, AVIF write = true. The Routes theory skips heic as target and as source (the fixture cannot be written); avif is fully covered.
- Task 4: ConversionRouter checks the source folder is writable by creating/deleting a temp file before calling the converter, and after any converter exception deletes exactly the paths the converter registered with `ctx.Track` (tracked folders recursively), then rethrows (see the Task 4 fix bullet).
- Task 4: ImageConverter decodes from bytes (content decides the decoder, so a PNG named .jpg works); Magick decode exceptions map to `LimeException("이미지를 읽을 수 없습니다.")` and encode/save exceptions to `"이미지를 저장하지 못했습니다."`. Alpha is flattened to white for jpg and bmp only. PNG uses define png:compression-level=6.
- Task 4: PDFsharp 6.5.0 turned out to be AGPL-3.0-only (license key required at runtime; 6.2.4 is the last MIT release). Pin lowered to 6.2.4 and referenced only by the test project; image->PDF is written with PdfPig's `PdfDocumentBuilder` (page = pixel size in pt, `AddPng` fills the page). PDF tests verify with PdfPig.
- Task 4: Enabled `CentralPackageTransitivePinningEnabled` and pinned transitive System.Security.Cryptography.Pkcs to 10.0.13 (8.0.1 and 10.0.0 carry NU1902/NU1903 advisories); build is warning-free.
- Task 4 fix: failure cleanup no longer diffs the folder. Converters call `ctx.Track(path)` for each output file/folder BEFORE creating it (`OperationContext.Created`, thread-safe); on any exception the router deletes only tracked paths (folders recursively), so files other processes create meanwhile are never touched. ImageConverter maps decode failures to "이미지를 읽을 수 없습니다.", encode failures to "이미지를 저장하지 못했습니다.", and source IO/permission errors to "원본 파일을 열 수 없습니다.".
- Task 5: PDF pages are rendered by PDFtoImage 5.4.0 (PDFium, SkiaSharp) at 200 DPI with the longest edge capped at 4096 px (explicit Width/Height computed from the page size in points), white background. Encoding uses SkiaSharp directly (jpg quality 80, png) instead of Magick; SkiaSharp comes in transitively. The original app uses 150 or 200 DPI depending on the path; this port uses 200 everywhere.
- Task 5: Every PDFtoImage/PDFium call goes through one static `SemaphoreSlim(1,1)` in `PdfRenderer` (PDFium is not thread-safe) and runs on a pool thread. The gate is taken per page, so cancellation is observed between pages. The PDF is read into a byte array once per call, so the source file is not locked while rendering.
- Task 5: PDF error mapping: password-protected (PDFium `PdfPasswordProtectedException` or PdfPig `PdfDocumentEncryptedException`) -> "암호로 보호된 PDF는 열 수 없습니다." with no prompt; empty, corrupt or otherwise unreadable -> "PDF를 읽을 수 없습니다."; PDF without any text -> "이 PDF에는 글자 정보가 없습니다. 도구 휠의 '글자 복사'를 쓰세요.".
- Task 5: pdf->txt uses PdfPig `ContentOrderTextExtractor` per page, pages joined by one blank line, UTF-8 without BOM. One-page PDFs produce a single `ConvertOutput` file, multi-page PDFs a `CreatePagesFolder` folder (tracked right after creation) with `PageFileName` files.
- Task 5: PDFsharp 6.2.4 core has no Windows font access (`UseWindowsFontsUnderWindows = true` still fails with "No appropriate font found"), so `FixtureFactory.Pdf` registers a small test-only `IFontResolver` that loads C:\Windows\Fonts\malgun.ttf (Malgun Gothic) for the Hangul text.
- Task 6A: `CapabilityDetector` (Core) treats Office as available only when `Word.Application`, `PowerPoint.Application` and `Excel.Application` each have a non-empty `HKCR\<ProgID>\CLSID`; Ffmpeg = `ffmpeg.exe` in a `PATH` folder (entries trimmed and unquoted, blank/malformed entries skipped; no PATHEXT or App Paths lookup). `FindOnPath` is public so it can be tested without touching the real PATH.
- Task 6A: `Services` is a static class (`Services.Start()` once in `App.OnStartup`; `Capabilities`, `Router`, `Jobs` throw if read before that). The router gets `ImageConverter` and `PdfConverter`, the converters that exist now.
- Task 6A: Win32 placement helpers live in one internal `Native.cs` (virtual screen, monitor at a point, GetAsyncKeyState, SetWindowPos, extended styles); the hook P/Invoke stays in `LowLevelHooks`.
- Task 6A: The hooks track left/right Shift/Ctrl/Alt separately and post a sample only when the modifier set, the left button, or (while the button is held, latest-point coalesced, at most one in flight) the cursor changes. Esc is the only other key looked at; nothing is stored. Injected events are skipped entirely.
- Task 6A: The drop overlay keeps the spike's exact window setup (no extra extended styles) and swallows `WM_DPICHANGED` so a surface spanning mixed-DPI monitors keeps its physical virtual-screen bounds. Petal hit-testing uses `GetCursorPos` (physical pixels) against the wheel centre and scale (physical px per canvas unit = wheel window width / 320).
- Task 6A: The wheel window is a fixed 320x320 DIP window with `WS_EX_TRANSPARENT|WS_EX_LAYERED|WS_EX_NOACTIVATE|WS_EX_TOOLWINDOW` so drops fall through to the overlay. It is moved twice (move, let WPF rescale for the target monitor's DPI, move again with the final size) and is clamped inside the cursor's monitor so every petal stays reachable near screen edges; the overlay hit-tests against the clamped centre.
- Task 6A: The wheel window and overlay are created once and hidden/shown per drag, not recreated.
- Task 6A: The drop returns `DragDropEffects.Copy` on a petal and `None` elsewhere; never `Move`, which would let Explorer delete the source.
- Task 6A: Tool and action petals start a JobRunner job that throws `LimeException("준비 중입니다.")`, so they show as a failed card titled with the petal label (closed by click) until their tasks land.
- Task 6A: Done and cancelled cards close themselves after 4 s; failed cards close on click. A done card with results opens `explorer.exe /select,"<first result>"` on click. The cancel button cancels the job's token and shows "취소하는 중…" until the job ends.
- Task 6A: Progress cards stack in one borderless topmost no-activate window (SizeToContent) in the bottom-right of the work area, 12 DIP margin. The monitor is the one under the cursor when the first card of a batch appears and stays fixed while any card is visible.
- Task 6A: "휠 켜기" is on at every start (not persisted). Turning it off uninstalls both hooks and closes any open wheel. The single-instance mutex is `Local\LimeWin.SingleInstance`; a second instance exits silently with code 0.
- Task 6A: H.NotifyIcon `ForceCreate(enablesEfficiencyMode: false)`: Efficiency Mode would lower the process priority and slow the hooks and conversions. The placeholder tray icon is a `GeneratedIconSource` "L" on lime green until Task 6B draws the real one.
- Task 6A: The app follows the system light/dark theme via `ApplicationThemeManager.ApplySystemTheme()` at startup and again on `SystemEvents.UserPreferenceChanged` (General/Color), since there is no main window for `SystemThemeWatcher` to watch. `NOTICE.md` is embedded into the exe as a resource for the license window.
- Task 6A: WPF-UI 4.3.0's implicit Window style sets `MinWidth=460`/`MinHeight=320`, which made the wheel window 460x320 (breaking its centring and hit-test scale) and padded the card stack. The overlay, wheel and card-host windows set `MinWidth`/`MinHeight` to 0 locally.
