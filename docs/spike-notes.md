# 드래그-휠 스파이크 결과 (Task 0)

일시: 2026-10-22, 환경: Windows 11 (빌드 26300), 모니터 2대(1920×1080 ×2, 둘 다 100%, 가상 화면 x −1920…1920), 마우스.
시험판: 저수준 마우스·키보드 훅(관찰만) + 가상 화면 전체를 덮는 투명 드롭 창(`#01000000`, Topmost, ShowActivated=False, AllowDrop). 코드는 버림.

## 판정: 통과

| # | 질문 | 결과 | 근거(로그) |
|---|---|---|---|
| 1 | 움직이지 않아도 덮개가 `DragEnter`를 받나 | **예** | 키 탭 → 덮개 표시 → 30–40 ms 뒤 `DragEnter FileDrop=True`, 커서 이동 0 |
| 2 | 원 안/밖에 놓으면 우리 `Drop`만 오고 탐색기는 아무것도 안 하나 | **예** | 고리·구멍·바깥(다른 폴더 위) 모두 `DROP received`, 사용자 확인: 파일 이동·복사 없음 |
| 3 | Shift/Ctrl/Alt 탭의 탐색기 부작용 | **없음** | 사용자 확인: Alt 메뉴 안 열림. 키를 삼킬 필요 없음 |
| 4 | Esc 취소, 다른 모니터에서 시작 | **정상** | Esc → 즉시 닫힘. 왼쪽 모니터(음수 좌표)에서도 `DragEnter`·`Drop` 정상 |
| 5 | 글자 선택·창 이동 드래그 중 키 탭 | **파일 정보 없음** | `DragEnter` 자체가 오지 않음 → 버튼 뗌에 닫힘 |
| 6 | 배율이 다른 모니터 | 시험 불가 | 이 PC는 두 모니터 모두 100% |

## Task 6에 주는 결론

1. **감지는 훅만으로 충분하다.** 25 ms 폴링 감지기도 붙여 비교했지만 매번 훅이 먼저 발동했다. 훅은 키를 삼키지 않는다.
2. **마우스 이동 없이 `DragEnter`가 온다.** 휠은 `DragEnter`에서 `FileDrop`을 받은 뒤에만 그린다(5번: 파일이 아니면 아무것도 그리지 않음).
3. **⚠ 버튼 뗌에 바로 닫으면 `Drop`이 사라진다.** 훅의 LBUTTON UP이 OLE `Drop`보다 먼저 처리되기 때문이다(1차 계측에서 확인).
   → 덮개가 `FileDrop` `DragEnter`를 받은 상태라면 버튼 뗌에서 "드롭 대기"로 바꾸고, `Drop` 처리 후 닫는다.
   500 ms 안에 `Drop`이 없으면 닫는다. 100 ms 안전 타이머도 드롭 대기를 존중한다. `FileDrop`을 못 받은 덮개는 즉시 닫는다.
4. 첫 시험에서 "아무것도 안 뜸"의 원인은 키를 버튼 뗌과 거의 동시에(뗀 직후 4–22 ms) 누른 것이었다. 버튼을 누른 채 탭하면 매번 동작했다. 사용 안내(README·환영 문구)에 "누른 채로 탭"을 적는다.
5. 혼합 DPI는 검증하지 못했으므로 Task 6은 모니터별 DPI(`PerMonitorV2`, 커서가 있는 모니터 기준 휠 배치)를 처리하고 체크리스트에 남긴다.
6. 계측 로그에 일반 키 입력을 남기지 않는다(시험 중 사용자의 타이핑이 기록됐던 문제). 본 앱은 키를 기록하지 않는다.
